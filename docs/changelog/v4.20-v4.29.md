### 4 個 commit(branch `claude/nice-feynman-wpW8l` PR #110)

**Bug B(`879787c`)— `indicators` lookback_days 真實切 series**

`src/fusion/indicator_assembly.py:80-94` `assemble_indicators` 收 `lookback_days=60`
但只用於 `fetch_facts`,series fetch 完全不知此參數 → 回 indicator_values JSONB
整 blob(~1500 天 series)。MACD 單 core ~182KB,5-core default preset → ~910KB,
逼近 MCP 1MB context limit。

修法:Python-level tail-slice — 在 `out[core]` 構造前對 `dict-typed` value 的
`series` list 取 `[-lookback_days:]`。`isinstance(series, list)` guard 對
pattern core 的 dict-shaped series 自動 passthrough。`fetch_indicator_latest`
signature 不動(3 個其他直 caller — stop_loss / market_dashboard / raw.query —
不受影響)。+4 tests(slice / shorter / non-list / non-dict)。

**Bug C(`43b0f86`)— `dual_track_resonance` batch query + 30s timeout 安全網**

`src/fusion/dual_track/track2.py:131-142` `read_track2` 對 3 horizons (21/63/126)
各 call `fetch_band`,fetch_band 內又對 6 source_core 偏好(fusion / kalman_cqr /
log_channel_cqr / chip_cqr / macro_cqr / fundamental_cqr)逐一發 SQL → **3 × 6 = 18
個 N+1 query**。雖能用 `idx_forecast_log_external` partial index,但每 query
prepare + index seek + libpq round-trip 累積,對大表 stock(2330 forecast_log
~1M rows)拖到 4 分鐘 timeout。

修法:
- 新加 `fetch_bands_batch` — 單 SQL 用 `ANY(%s::int[])` + `ANY(%s::text[])` 顯式
  cast 取多 horizon × 多 source_core(Plan agent caveat:psycopg 對 Python list
  推 SMALLINT[] / TEXT[] 不保證);Python 端依 `_SOURCE_PREFERENCE` rank 取每
  horizon 首選(deterministic via `uq_forecast_log_lookup` unique constraint)
- 抽 `_row_to_band` helper 共用 width_ratio / is_overly_wide 防呆邏輯
- `fetch_band` 公共簽章保留,改為 `fetch_bands_batch` 的 backward-compat shim
- `read_track2` 18 → 1 query,2330 timeout > 240s → < 1s
- **`mcp_server/tools/data.py::dual_track_resonance` 加 30s statement_timeout 安全網**
  (user 拍版,2026-05-27):wrapper 自己開 conn → `SET LOCAL statement_timeout = '30s'`
  → 傳 conn 給 `resonance()`。`QueryCanceled` 接住回 graceful error dict(含 diagnostics
  給 LLM 知道 root cause),其他 exception 正常 propagate 避免靜默誤判。`SET LOCAL`
  限本 transaction,conn close 後不影響其他 query;只在 MCP tool wrapper 設,
  不動 library code(dashboard / direct caller 不受影響)

+8 batch test(returns_preferred_source / kalman_fallback / missing_horizon /
empty / empty_horizons / internal_only_filter / explicit_cast / read_track2
single_batch)+ 3 MCP wrapper test(timeout_graceful_error / non_timeout_propagates
/ sets_statement_timeout)。

**Bug A(`b2096b3`)— `monthly_revenue` Silver builder 改從 raw revenue 算 YoY/MoM**

`monthly_revenue_derived.revenue_yoy = 2026.0`(calendar year)汙染 3 個 MCP
tool:`stock_snapshot.fundamentals` / `monthly_screen.revenue_momentum` /
`monthly_trigger_scan.positive_triggers`。後者因 2026 > 30 threshold 全通過,
positive_total 從個位數膨脹到 387 個,production 不可用。

**Root cause(自 PR #18.5 以來邏輯錯誤)**:`silver/builders/monthly_revenue.py:50-51`:
```python
"revenue_yoy": row.get("revenue_year"),    # ★ BUG:calendar year 當 YoY%
"revenue_mom": row.get("revenue_month"),   # ★ BUG:calendar month 當 MoM%
```
FinMind `TaiwanStockMonthRevenue` 的 `revenue_year` / `revenue_month` 實際是
**該筆營收的日曆年份 / 月份**(e.g. 2026.0 / 4.0),非 YoY% / MoM% 百分比。
此 dataset **不提供** YoY% / MoM%,需自行從 `revenue` 跨月計算。

**強證據鏈**:
- `src/forecast/fundamental_forecast.py:96-128` `_compute_yoy_3m_avg` 把
  `revenue_year` / `revenue_month` 當 `(year, month)` calendar tuple 用
  (`by_period[(y, m)] = rev` / `base_key = (y - 1, m)`),然後從 raw revenue 算 YoY
- M8 v4.24 production verify(8-stock 跨產業 24/24 wins,`fundamental_cqr` h=21
  pinball 10.20 / h=126 27.07)反證 — 若 `revenue_year` 是 YoY%,fundamental_forecast_core
  用 `(yoy_pct, mom_pct)` tuple 永遠 match 不到 `(yoy-1, mom)`,fusion 不會出
  `fundamental_cqr` 訊號 — but it does work

修法:
- Silver builder 改 `_build_period_index` 建 `(market, stock_id, year, month) →
  revenue` index,per-row 算 `(rev - base_yoy) / base_yoy * 100`(decimal × 100
  = percent),Jan 的 MoM 用 `(prev_year, 12)` wrap-around
- `_fetch_all_bronze_rows` bypass v4.15 incremental 180d READ window — YoY 需
  13+ 月 history;monthly_revenue 體量小(每股 12 月/年 × 7 yr × ~1300 股 ≈ 110k
  rows total)全 fetch < 1s,wall time 影響微乎其微
- Bronze schema 不動,Silver schema 不動(`revenue_yoy NUMERIC(10, 4)` 範圍夠存
  雙位數百分比)
- 下游 caller 0 改動 — `monthly_trigger_signals_derived` / `revenue_momentum_ranked_derived`
  / `stock_snapshot.fundamentals` 都讀 Silver.revenue_yoy,value 從 wrong → correct

yoy_skip_zero_base / yoy_negative / per_stock_isolation / full_build_integration

### Root cause

Fusion 設計基礎是 forecast combination puzzle(Bates & Granger 1969 / Stock &
Watson 2004 / Smith & Wallis 2009):**多 uncorrelated forecaster 等權平均通常勝
過任一單一 forecaster**。前提是**誤差 uncorrelated**。

目前 3 cores 全部基於同一 daily close price:
- `baseline` — 21-126 天歷史 return 經驗分位數
- `kalman_cqr` — LLT 平滑 + CQR
- `log_channel_cqr` — log(close) trailing OLS + CQR

**全是 price-only signal,同源 → 誤差高度相關 → 違反 Bates-Granger 前提 →
fusion 無 variance reduction 空間**。

Intersection 主路徑:log_channel_cqr 區間 3× 寬於 kalman_cqr → 交集 ≈
kalman_cqr 邊界 → fusion ≈ pass-through + selection bias(只在 kalman_cqr 過去
勝 baseline 才寫 → 子集偏難)。

### 拍版:保留 fusion + 記錄限制(2026-05-23)

**不**移除 fusion:
